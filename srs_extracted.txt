Purpose. This specification defines a secure, phased product that reviews Python and JavaScript code, explains findings, suggests safe fixes, and progressively adds repository-aware automation. Phase 1 deliberately proves the end-to-end review experience before the product integrates external source-control systems or applies changes.
1 Introduction
1.1 Purpose
The system provides an AI-assisted code-review workflow that combines deterministic checks with agentic reasoning. It is intended to help developers identify correctness, maintainability, and security issues earlier, while keeping humans responsible for approval and merge decisions.
1.2 Scope
The product accepts pasted code and uploaded files in Phase 1. Later phases add static-analysis adapters, GitHub repository ingestion, comprehensive reports, patch validation, pull-request reviews, policy-aware routing, and multi-agent orchestration. It does not autonomously merge code, access production systems, or execute untrusted project code outside a controlled sandbox.

1.4 Product goals
Deliver useful, explainable findings for Python and JavaScript in a first working prototype.
Prioritize security-critical issues and reduce noisy, non-actionable output through evidence and confidence scoring.
Provide an extensible architecture for tool-backed analysis, repository context, and pull-request feedback.
Preserve developer control, source-code confidentiality, and auditable decisions.
1.5 Out of scope
Native IDE plugins, autonomous remediation in protected branches, support for every programming language, continuous production monitoring, and legal compliance certification are excluded from the initial release. They may be evaluated after the defined milestones.

3.2 Assumptions and constraints
The user has authority to submit the source code and accepts the configured model-processing terms.
Phase 1 supports UTF-8 source files up to 250 KB per file and a single-file review; multi-file context is deferred.
AI output is advisory. Severity, confidence, and source evidence must be visible to users.
Third-party static analyzers and GitHub access are feature-flagged integrations with least-privilege credentials.

6 Architecture overview
The architecture separates the interactive control plane from isolated analysis execution. A browser client submits a review request to an API gateway. The Review Orchestrator creates a run, retrieves policy, dispatches deterministic and AI agents, normalizes results, and sends a signed result to the reporting service. Repository and patch-validation capabilities remain isolated behind integration and sandbox boundaries.

6.1 Logical processing sequence
Submit -> validate and classify -> create review run -> load policy -> parse and deterministic scan -> AI reasoning -> normalize and score -> policy gate -> persist -> present results. In repository-enabled phases, the sequence additionally snapshots the selected revision, limits context to scope, and creates immutable provenance links.
6.2 Deployment topology
Public web application and API gateway in a segmented application network.
Queue-backed worker pool for parser, tool adapter, report, and agent tasks.
Encrypted relational database for metadata and findings; encrypted object store for uploaded source and reports.
Managed secret store for OAuth tokens, signing keys, and model-provider credentials.
Dedicated, non-production sandbox cluster with no default egress and no access to tenant secrets.

7.1 Agent orchestration rules
Each agent receives the minimum necessary context and a signed run-scoped authorization.
Agents exchange typed JSON contracts; free-form prose cannot independently create a blocking security finding.
The orchestrator enforces budget, deadline, retry, and stop conditions; loops require a maximum iteration count.
A human decision is required before applying a patch, changing repository settings, publishing external comments where policy requires it, or merging code.

8.2 Repository and PR workflow
A maintainer installs a GitHub App with the minimum repository permissions. The integration service exchanges and stores encrypted installation credentials, receives a selected revision or webhook event, and creates an immutable repository snapshot. The orchestrator limits analysis to changed files plus approved contextual files. It runs static tools, agent review, and optional validation. The PR Review Agent generates a draft summary and comments; a configured policy determines whether a human must approve publication. No agent may merge, push, or alter branch protection settings.
8.3 Patch validation workflow
A user selects a patch candidate. The system creates a new patch-validation run with the base revision, diff, and allowlisted commands. An isolated sandbox checks out only the snapshot, applies the diff, runs lint/build/test tasks with CPU, memory, disk, time, and network constraints, and returns logs after redaction. Validation success means only that the configured checks passed; it does not guarantee correctness or security.

9.1 Data retention and lifecycle
The default Phase 1 retention is 30 days for source artifacts and 90 days for normalized findings, configurable per tenant. Users may delete a submission unless a legal hold or administrator policy applies. Backups follow the same encryption and deletion schedule. Audit records retain identifiers and actions but exclude full source excerpts and credentials.

10.2 Finding contract
A finding response contains finding_id, run_id, origin (tool or agent), rule_id where applicable, category, severity, confidence, title, rationale, remediation, evidence[] with source ranges, related_finding_ids, patch_candidate_id if present, and disposition. The contract shall reject unbounded HTML, executable payloads, and source excerpts beyond configured limits.
11 Security and privacy
11.1 Threat model priorities
Threat
Required mitigation
Malicious source or prompt injection
Treat source as data; isolate delimiters; prohibit tools and policy changes through model output; validate JSON schema.
Credential compromise
Use vault-backed short-lived tokens, least privilege, rotation, redaction, and audit.
Cross-tenant data exposure
Tenant IDs enforced in every query, object-store prefix, queue payload, and authorization decision.
Unsafe code execution
No Phase 1 execution; later run only in disposable sandboxes with no secrets, limited egress, and quotas.
AI hallucination or false confidence
Evidence links, confidence, deterministic corroboration, human approval, and policy thresholds.
Dependency or tool supply-chain risk
Pin versions and images, scan artifacts, verify signatures where available, and maintain SBOMs.
Denial of service
Rate limits, upload limits, request budgets, queues, circuit breakers, and per-tenant quotas.
Sensitive data in logs
Structured redaction, content-free telemetry, access controls, and periodic log review.
11.2 Authorization model
Roles are Viewer, Developer, Reviewer, Security Analyst, Repository Maintainer, Tenant Administrator, and Platform Operator. Permissions are additive but constrained by tenant and repository policy. Only Tenant Administrators manage integrations and retention. Repository Maintainers approve repository-level settings. Platform Operators cannot read tenant source by default.
11.3 Secure development requirements
Use SAST, dependency scanning, secret scanning, and code review for the product itself.
Maintain threat-model reviews for each new integration, agent tool, and sandbox image.
Run penetration testing before external repository integration general availability.
Maintain incident response playbooks for credential exposure, data access, model-provider outage, and sandbox escape signals.

12.1 Quality gates
A release cannot proceed when Critical known-vulnerability detection regressions are unresolved, tenant-isolation tests fail, source content appears in prohibited logs, a public API contract breaks without a version increment, or the model-output schema failure rate exceeds the agreed operational threshold. Evaluation datasets must be versioned and segregated from tenant source.

13.2 Release strategy
Use infrastructure as code, immutable container images, signed build artifacts, automated migrations, and feature flags. Deploy canary releases per tenant or cohort. Roll back stateless services by version; use forward-compatible database migrations and a documented rollback plan. Static-tool and model-prompt/config changes are versioned separately from application code.
13.3 Operational metrics
Track run volume, completion and failure rate, queue depth, latency percentiles, agent timeout/schema failure rate, per-tenant cost, finding rate by severity, duplicate rate, feedback usefulness, false-positive dispositions, validation pass rate, PR comment publication rate, and security events. Alert on data-boundary failures, credential errors, sandbox policy violations, elevated timeouts, and model-provider degradation.

14.1 Phase 1 release acceptance criteria
A user can successfully paste or upload valid Python/JavaScript code and receive a persisted review result.
The system catches representative seeded issues from the Phase 1 evaluation corpus, including an exposed secret, Python eval use, JavaScript injection pattern, and insecure deserialization pattern.
Every displayed finding includes severity, confidence, explanation, and code evidence or an explicit location limitation.
Unsupported files, malformed input, and parser errors are handled without a server error or model call where parsing is required.
The product does not execute submitted source, and automated security checks confirm the guarantee.
Users can retrieve their own review and request deletion; unauthorized users cannot access it.
The median and p95 review time meet NFR-001 under the Phase 1 load test target.
